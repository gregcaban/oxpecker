## Where things stand

**The generation layer has been deleted and is to be rebuilt from Fuzzilli's design.** Nothing
currently generates programs. What works: the Java harness, `compare`, `findings`, the corpora,
the UI code, and the commands `oxpecker run | diff | corpus | probe`. `pytest tests/` → 50 passed.

Why it was deleted: the IR generators (ported from the old string generator, mostly by parallel
Sonnet workers following a guide I wrote) were string generators in disguise — 105 of 133
generators emitted JavaScript text through an `Eval` escape hatch, "literals" that were code,
code-like branch labels and bare-string vocabularies. The user found it by reading the code and
was rightly disappointed; I had accepted the work on passing tests. Full account and the
specification for the replacement: `docs/what_went_wrong_with_ir_generators.md`.

User decisions (2026-10-25/26):
- Whole generation side rebuilt as a new package designed from FuzzIL; nothing carried over by
  default — a piece of the old IR comes back only by deliberate re-introduction and review.
- Old string generator deleted now, not kept until parity.
- No `Eval` in the generation layer at all; no JS text anywhere except the lifter's output;
  enums for closed vocabularies (operators, keywords), typed registries for builtins/keys/methods.
- Credit Fuzzilli in EVERY file derived from it (Apache-2.0 header naming the Swift source).

## Gotchas

- Hypothesis skips shrinking an example it finds under a test's *primary* database key (the
  "reused previously shrunk" fast path in `engine.py`); a failure to be shrunk goes under the
  `.secondary` sub-key, as `fuzz_one_input` does. `fuzz.Shrinker` learned this the hard way
  (one shrink call, same program back).
- Hypothesis (6.170) sometimes answers a draw with a constant scraped from the source of any
  loaded module; seeded draws go through `strategies.SeededProvider` so a seed means the same
  program in the shell, the CLI and the tests (G43). Symptom before the fix: the golden test
  failed only after `test_cli.py` or `test_fuzz.py` had run.
- Extending a corpus entry replays its whole lineage (base generation plus every step): 250 ms
  against 97 ms for a fresh program and 201 ms for Rhino. The step cap (5) bounds it but makes
  entries at the cap dead ends. Both are measured and designed in
  `docs/il-refactor-followup-work.md` (cache the parent; rebase), with `combine`'s dominance of
  the corpus and the missing rejection statistics.
- A first 150-run campaign (`oxpecker fuzz`, 2026-10-26): ~5 runs/s with coverage, the corpus
  grows by about one entry per two runs early on, half the runs log `java-types` differences,
  and the only hard signatures were the expected `compiled=unsupported(continuations)` pair,
  now in `tests/known_signatures.txt`.

- `harness-java/build/libs/oxpecker-harness-all.jar` was rebuilt for `9ed5a22`; rebuild with
  `cd harness-java && ./gradlew fatJar` after any Java change. Don't rebuild while harness runs are
  in progress (a JVM loading classes lazily from a replaced jar fails oddly).
- Coverage tests need `bin/harness` with `OXPECKER_COVERAGE=1` (the client sets it when
  `coverage=True`) and `harness-java/build/libs/jacocoagent.jar`.
- Hypothesis 6.170.5 facts verified in source this session: `fuzz_one_input` saves failures under
  `<digest>.secondary` (the local is misleadingly named `database_key`, core.py:2337); on
  misalignment only the one draw gets the index-0 value, later draws keep their positions;
  `@seed` disables database writes; `BUFFER_SIZE = 8*1024` caps serialized choices per test case.
- `oxpecker.egg-info/` shows modifications and `uv.lock` is untracked — not mine; leave them.
- Rhino accepts `function () {}` as a statement (an anonymous function declaration node rejects).

### Gotchas from implementing `oxpecker/il/` (2026-10-26)

Hypothesis seams (6.170.5):
- `strategy.example()` runs a strategy several times and caches; a strategy that mutates a
  `Builder` emits into it repeatedly and corrupts it. Use `strategies.draw(strategy, seed)`
  (one `ConjectureData` + `BuildContext(data, wrapped_test=lambda: None)`) or `generate(seed)`.
  Tests are written against those; `NonInteractiveExampleWarning` is treated as an error.
- `.map`/`.filter` on a strategy drawn outside a `@given` test need a build context; `maybe(p)`
  is therefore `sampled_from` of a fixed bool list (and shrinks to `False`).
- `@st.composite` on a function that never calls `draw` is a deprecation warning (treated as an
  error in the suite): helpers that only build IL are plain functions taking the builder.
- `hypothesis.note()` outside a test raises `InvalidArgument`; the Rhino parse helper guards it.
- 40 examples of `st.integers(0, 4)` do not cover every value (boundary bias). "Some draws must
  emit X" expectations in `test_generators.py` list only the common shapes.

FuzzIL rules the builder enforces (the structure tests hit them first):
- Values used by an object literal or a switch must be loaded before the literal/switch opens:
  `LoadInteger` needs `Context.JAVASCRIPT`, not `OBJECT_LITERAL`/`SWITCH_BLOCK`. Draw the
  value, then open the block.
- The output of `BeginCodeString` is visible inside the code string (it is the string); the
  lifter declares its name before lifting the inner program, so inner references resolve.
- Function begins are constructed with keyword arguments (`param_types` sits after
  `parameters`); `Operation.name` is a property, so no op may have a `name` field.

Harness observation points:
- `J.typeOf(x)` is not where Integer-vs-Double shows: Rhino converts a number argument to a
  Java `Object` parameter to Double in every mode. `__probe(...)` records the raw class per
  argument in `Outcome.traceJavaTypes` as `"String | Double | Integer"` (the label first).
- `Outcome.value` prints Java objects opaquely (`[Java java.lang.String]`); wrap a Java-returned
  string in `String(...)` if the script's completion value must show it.
- An engine exception past JS try/catch (`status == "crash"`, `engineException`) is a Rhino
  finding in both modes; the completion test prints it with its seed rather than failing.

Rhino `b95f75d` facts found by the oracle tests:
- No `d` (hasIndices) and no `v` regexp flags.
- `"use strict"` inside a function with a rest/default/destructuring parameter is a SyntaxError
  (`verify` rule "strict"; `strict_function` draws simple parameters).
- `new Int16Array(n).set()` throws `ArrayIndexOutOfBoundsException` (regression recorded).
- In an optimizer-run function `p + 1` with a parameter `p` is boxed as Double (Codegen's
  `add(Object, double)`), the activation copy keeps Integer: G32, not yet in `expr_type`.

Repo conventions that bit:
- The lint (`tests/il/test_lint.py`) scans every string constant in `strategies.py`,
  `templates.py` and `generators/`, skipping docstrings, `load_string(...)` arguments,
  `__repr__`/`__str__` bodies and `raise` messages. Error messages elsewhere must not contain
  JavaScript tokens; property names come from `Keys.*` (`Keys.A.name` when a string is needed).
- Generator pools are ordered by family, then `rank`, then name; a value maker that should be
  first in a fallback (integer) carries `rank=0`.
- In zsh `echo ====` and unquoted `--include=*.java` fail (`=` expansion, globbing).
